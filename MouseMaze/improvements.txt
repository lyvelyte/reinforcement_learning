MouseMaze training improvement plan
===================================

Goal
----
Train a policy quickly on new, fully observable 11x11 mazes while keeping the
training system reusable for other finite-action reinforcement-learning tasks.
The word "solve" below means a greedy (no exploration) policy reaches the goal
within the environment's time limit on previously unseen tasks.

Important expectation
---------------------
An 11x11 full-map maze is a planning problem, not a partially observed one. A
neural RL policy can become very reliable, but it cannot honestly promise to
solve every possible maze. The current environment already computes a BFS
distance map, so an exact planner can solve every reachable maze immediately.

If "every time" is a product requirement, expose an optional generic planner
fallback: use a transition-model/search interface when one is available, and
use the learned policy otherwise. In MouseMaze, the implementation is BFS or
A*; in another problem it can be any domain-supplied planner. This preserves
reuse and makes the guarantee explicit instead of attributing it to a DQN.

Evidence from the current log (2026-07-09)
-------------------------------------------
* The completed DQN run collected 2,135,579 environment steps in 1,626 seconds
  (about 1,314 steps/s). Its best greedy solve rate was 44%; its final greedy
  solve rate was 34% after 50,000 episodes.
* In that run, solved mazes had 100% optimality and zero invalid moves. The
  policy therefore knows how to follow a shortest path in some cases, but does
  not generalize to enough unseen maps.
* A partial PPO run was faster (about 2,620 steps/s) but had a best solve rate
  of only 24.5% and many loop/repeated-state-action failures. Do not make PPO
  the default until an equal-budget benchmark demonstrates a clear win.
* The log shows one CPU core close to 100% while GPU use is commonly low. The
  Python per-environment stepping/observation construction is the immediate
  throughput bottleneck, not GPU memory or a lack of model capacity.

Implementation sequence
-----------------------

Phase 0 - Establish a trustworthy benchmark before tuning

1. Add a BenchmarkConfig and a small command such as `--benchmark` that runs
   fixed train seeds and three disjoint evaluation suites: validation, final
   test, and stress test. Derive their seeds from a root SeedSequence; never
   reuse a training RNG for an evaluation suite.
2. Report metrics by difficulty bucket rather than only one aggregate rate.
   For MouseMaze the initial buckets should be shortest-path length 1-8, 9-16,
   17-24, and 25+; the generic TaskSampler should provide the bucket label.
3. Retain solve rate, path-cost/optimal-cost, timeout rate, and action count.
   Add a bootstrap 95% confidence interval for solve rate and record the
   number of mazes, seed, algorithm, and total environment transitions.
4. Add two reference policies to every benchmark: uniformly random among legal
   actions, and an optional domain oracle. The BFS oracle must get 100% on
   reachable MouseMaze maps; otherwise the environment/generator is defective.
5. Use validation only for checkpoint selection. Run the final test once after
   selecting the checkpoint, with at least 2,000 unseen mazes. For the claim
   "every time", also run 10,000 stress mazes with zero failures; present this
   as empirical coverage, not a mathematical guarantee for a neural network.

Acceptance gate: first reproduce the current DQN result under this harness.
Do not compare algorithm changes until they use the same seeds, task budget,
evaluation suites, and wall-clock measurement.

Phase 1 - Make task generation and curriculum general-purpose

1. Replace the fixed `curriculum_distance_range` branches (which only activate
   for exactly `(11, 11)`) with a TaskSampler protocol:

       sample(rng, difficulty) -> environment
       describe(environment) -> {"difficulty": numeric_value, "bucket": str}

   MouseMaze should report shortest-path length and optionally maze dimensions
   and branch count. Other tasks can use their own meaningful difficulty
   signal, or leave it absent and use uniform sampling.
2. Replace fixed episode cutoffs with a performance-gated curriculum. Start at
   easy tasks; promote only after validation solve rate is at least 90% for
   three consecutive evaluations. Keep 20% of samples from earlier buckets to
   prevent forgetting, and keep 10% uniformly sampled from the complete task
   distribution. Make all percentages configuration fields.
3. Stop retrying an arbitrary number of maze generations in the training hot
   loop. Build a per-bucket task cache during setup, refill it asynchronously
   or in batches, and log a sampling failure if a requested bucket is empty.
   The sampler interface, rather than the DQN, owns this behavior.
4. Keep action validity as an optional ActionMask interface. The environment
   supplies a Boolean mask; the agent masks policy choice, random exploration,
   and bootstrap targets. If no mask is supplied, all actions remain legal.
   This is useful beyond mazes (invalid API calls, constrained control, etc.).

Acceptance gate: each curriculum bucket has a nonzero validation solve rate,
and promotion occurs from recorded metrics rather than a hard-coded episode
number or maze size.

Phase 2 - Improve the data/training contract

1. Make `total_env_steps` the sole time base for epsilon, warm-up, evaluation,
   target updates, logging, and checkpoint names. Episode counts vary with
   task difficulty and with `num_envs`, so they are unsuitable as a portable
   training clock.
2. Rename `train_updates_per_step` to either `gradient_steps_per_collect` or
   `updates_per_transition`, then log the derived update-to-data (UTD) ratio.
   With 64 environments, the current value of four means 4/64 = 0.0625 DQN
   updates per newly collected transition, not four updates per transition.
   Sweep UTD values 0.125, 0.25, and 0.5 before trying larger values.
3. Add an explicit random-data warm-up in transitions (start with 10,000 for
   the 11x11 experiment), then train at the chosen UTD. This makes the first
   batches diverse and prevents a short easy-task prefix from dominating the
   Q-function.
4. Schedule epsilon by transitions. First experiment: linearly decay 1.0 to
   0.10 over the first 25% of the training transition budget, then 0.10 to
   0.02 over the next 50%. Evaluate only with epsilon zero. Retain the old
   schedule as a benchmarked option rather than silently changing it.
5. Make target-network synchronization transition based. Compare a soft update
   (`target = 0.995 * target + 0.005 * online` after each optimizer step) with
   a hard update every 5,000-10,000 transitions. The current 2,000 optimizer
   update interval changes its behavior whenever vectorization or UTD changes.
6. Add optional prioritized replay (proportional priorities, alpha=0.6,
   importance-sampling beta annealed from 0.4 to 1.0). Store priorities beside
   the existing preallocated arrays, update sampled items from absolute TD
   error plus epsilon, and keep uniform replay as the default comparison.
   This is a reusable replay component, not maze-specific logic.
7. Checkpoint enough state to make `--resume` meaningful: online/target model,
   optimizer, schedule counters, best-validation score, Python/NumPy/Torch
   (including CUDA) RNG state, task-sampler RNG state, full TrainConfig, and
   optionally replay data and priorities. Save atomically to a temporary file
   and then rename. Document when a resume deliberately starts with empty
   replay instead of calling it exact resume.

Acceptance gate: at least one DQN configuration exceeds the current 44% peak
on the fixed validation suite with no more transitions, and it is stable across
five training seeds before it becomes the default.

Phase 3 - Use the full-view signal efficiently

1. Introduce an optional ExpertPolicy/Planner interface:

       optimal_action_distribution(state, action_mask) -> probabilities

   For MouseMaze, select all legal neighbours whose BFS distance is exactly one
   lower than the current cell. Support multiple equally optimal actions so the
   interface also applies to graphs that are not perfect mazes.
2. Add a behavior-cloning pretraining mode using cross-entropy/KL loss on
   planner-labelled states from generated tasks. Generate labels for every
   reachable cell in a maze, not merely the start-state trajectory. Train on a
   held-out task split, then either (a) use the policy directly or (b) use its
   weights to initialize DQN and continue RL fine-tuning.
3. Add an optional auxiliary head that predicts normalized cost-to-go from the
   full observation. Train it with Huber loss from the expert labels and apply
   a small, configurable loss weight. This turns the available dense planning
   signal into representation learning instead of relying solely on shaped
   reward. The head must be generic: it is enabled only when a task provides a
   cost-to-go label.
4. Keep the existing potential-based shaping behind a PotentialFunction
   protocol. The current BFS potential is valid for MouseMaze, but no generic
   agent should require maze distance or `manhattan_to_goal`. Include a test
   that the potential is zero at terminal states and that toggling it off still
   leaves a valid sparse-reward environment.

This phase is the shortest route to a highly reliable full-observation maze
policy. It remains reusable because an environment may opt into an oracle,
demonstrations, a potential, all three, or none.

Phase 4 - Remove the measured performance bottlenecks

1. Create a batched/vectorized environment API with `reset_batch()` and
   `step_batch(actions)`. MouseMaze's implementation should keep grids, wall
   maps, goal locations, agent locations, step counts, and BFS maps in NumPy
   arrays shaped `(num_envs, ...)`; calculate legal moves and rewards using
   masked array operations. Keep the existing single Maze class for rendering
   and a generic synchronous adapter as the compatibility fallback.
2. Preallocate/reuse batched observations and action masks. The current code
   repeatedly builds Python lists, calls `np.stack`, allocates a full
   observation for each step, and loops over every environment. The vectorized
   path must return the same values as sequential Maze instances for a fixed
   seed and action sequence.
3. Optimize only after profiling the vector environment. Candidates are:
   cache the spatial coordinate planes as registered buffers instead of calling
   `torch.linspace` every forward pass; add configurable 32-channel/2-block
   and 64-channel/6-block spatial trunks; and benchmark `torch.compile` behind
   a flag. Select the smallest model that reaches the accuracy gate.
4. If profiling shows host-to-device copies are material, store replay in
   preallocated pinned Torch tensors, gather a batch with `index_select`, and
   transfer with `non_blocking=True`. Benchmark batch sizes 512, 1024, and 2048
   only after the vector environment is in place.
5. Decouple monitoring from training: during search evaluate 32-64 validation
   tasks every 10,000 transitions; before a checkpoint/final report evaluate
   2,000+ tasks. Keep the dashboard in the main process and make it opt-in.
   This prevents evaluation from consuming a large and variable fraction of a
   small task's wall-clock budget.

Acceptance gate: profile before/after on the same hardware and configuration.
Target at least 2x the current DQN collection throughput without reducing the
fixed-suite solve rate. Report environment, inference, optimization, and
evaluation time separately.

Phase 5 - Algorithm selection and default configuration

1. Treat DQN, PPO, behavior cloning, and planner-assisted fine-tuning as
   experiments that implement a common Agent protocol. Do not mix algorithm
   policy into Maze or task-generation code.
2. Start the next experiment matrix with DQN plus vectorized collection,
   transition-based schedules, performance-gated curriculum, and uniform
   replay. Compare prioritized replay and soft targets one at a time.
3. Run PPO only after fixing its evaluation cadence to use transitions and
   after adding diagnostics for policy entropy, approximate KL, clip fraction,
   explained value, and per-bucket loops. Its present partial run is not a
   competitive baseline.
4. Suggested success criteria for a new default are median validation solve
   rate >=95% over five seeds, lower 95% confidence bound >=90% on each
   difficulty bucket, path cost no worse than 1.10x optimal on successes, and
   final-test results that agree with validation. Raise the target toward 99%
   after the planner/distillation path is available.

Required tests for the implementation work
-------------------------------------------
* Vectorized MouseMaze and sequential Maze produce identical observations,
  masks, rewards, done flags, positions, and distances for seeded action traces.
* A BFS oracle solves every generated reachable maze and its labels contain
  only legal, distance-decreasing actions.
* A no-oracle dummy task can still train/evaluate through the shared interfaces.
* Epsilon/target/evaluation schedules trigger at exact transition counts and
  are unchanged by altering `num_envs`.
* Prioritized replay samples high-priority records more often and applies
  correctly shaped importance weights; uniform replay remains deterministic
  with a fixed NumPy generator.
* Save/load restores schedules and RNG state; exact replay resume is bitwise
  reproducible for a short CPU run when replay persistence is enabled.
* Benchmark suite partitioning has no seed overlap, checkpoint selection uses
  validation only, and final-test execution does not alter training RNG state.

Files likely to change when this plan is implemented
------------------------------------------------------
* `MouseAgent.py`: split generic protocols, vector environment adapter, DQN
  schedule/replay changes, checkpointing, benchmark CLI, and smaller
  independently testable training functions.
* `gen_maze.py`: accept deterministic per-task RNG/seed and optionally return
  task metadata; keep maze-specific generation out of generic agent code.
* New focused modules are preferable once code moves: `envs.py`, `replay.py`,
  `agents.py`, `benchmark.py`, and `experts.py`. Avoid adding another large
  all-in-one module.
* `test_mouse_agent.py`: retain existing observable-behaviour tests and add
  the regression tests listed above. Do not use GUI/dashboard tests for core
  training correctness.

Recommended first implementation slice
--------------------------------------
Implement Phase 0 plus the transition-based DQN schedule from Phase 2, then
run the five-seed benchmark. Next implement vectorized MouseMaze and prove its
equivalence with the current Maze. Only then add planner-label pretraining.
This order produces a reliable baseline, identifies the true throughput gain,
and prevents a high reported score from hiding evaluation leakage or a
maze-specific shortcut.
